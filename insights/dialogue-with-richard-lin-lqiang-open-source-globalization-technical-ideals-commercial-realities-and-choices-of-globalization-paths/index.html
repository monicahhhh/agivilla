Relationship between Open Source Projects and Foundations

Monica

Hmm, first, congratulations to Richard for finding such an excellent platform. I have a question here: What is the relationship between an open source organization and a foundation after donating a project to a US foundation? Could you elaborate on aspects such as ownership and future development?

Richard

First, we need to clarify a few core concepts: open source project, open source licensing, and project donation. These three are not the same. Let's talk about copyright and ownership first – whether it's a company or an individual, when a software work is developed, from the perspective of copyright law, they naturally own the copyright to that work. It's like selling music or copyrights in the past; if you create something, you have the corresponding rights. Some places require registration, for example, China requires software copyright registration, and the US requires registration with the Library of Congress. But regardless of registration, the copyright itself exists.

Once you own the copyright, you have many choices: you can keep it proprietary and sell it, give it away for free, or authorize others to use it through open source. It's important to note here that the core of open source is "licensing." It's like IP licensing – I grant you the right to use it, but the ownership is still mine. I'm just licensing certain rights for you to use.

Open source licensing follows the same logic: as the copyright owner, I put the project code on platforms like GitHub through an open source license, and anyone can view and use it. Any legitimate GitHub project will state the open source license used in its README file, and there will also be a LICENSE.TXT file in the root directory clearly indicating which open source license it is. Because there are many standard open source licenses globally, these licenses are managed by an organization called OSI (Open Source Initiative). If you invent your own open source license, it doesn't count; it must be submitted to OSI for review, and only after approval can it be called an "OSI-approved standard open source license." Of course, there are also non-standard open source licenses, such as Dify, which are based on standard licenses but modified to add some commercial protective clauses.

Common standard open source licenses include Apache 2.0 (related to the Apache Foundation, to which our company's project was donated), GPL (related to the Free Software Foundation, used by the Linux kernel), MIT (from the Massachusetts Institute of Technology), and BSD (from the Berkeley Software Distribution). There are hundreds of such standard licenses globally.

Now, back to your question: open source licensing and donating a project to a foundation are two different things. If a company merely open sources a project without donating it to a foundation, the ownership of the project still belongs to that company. The open source license merely defines the "rules of the game" for others using the project – for example, you can use it for free and develop it further, but if you commercialize and sell your derived product, you must inform your customers that it's based on which upstream open source project, giving credit to the original author. At the same time, if your derived product has problems, customers cannot hold the original author accountable, because open source is free licensing, and the original author does not bear liability for product defects.

For example, if you use my open source software for secondary development and then sell it to a customer, and the customer encounters problems, you should be held responsible, not me. This is different from the food supply chain – if your pre-made dish uses my ingredients and causes problems, it might be my responsibility. But open source software is different; unless it can be proven that the original author intentionally engaged in "open source poisoning" (embedding malicious code), the original author is not responsible for defects because the software is provided for free.

Let's talk about donating a project to a foundation. The two most well-known open source foundations globally are the Linux Foundation and the Apache Software Foundation. Why donate a project? The core reason is to assure users of the project's long-term sustainability. Some open source projects belong to a company, which might later change the license or close source and charge, like getting users "addicted to opium" before harvesting them. While this practice is legal, it damages community trust. After donating to a foundation, the project cannot be arbitrarily closed source or have its license changed. Even if the donating company goes out of business, the foundation might find someone to take over maintenance, allowing the project to continue developing.

Our company's Gravitino project was donated to the Apache Foundation precisely to give global customers peace of mind. The same applies to any startup: there are only three outcomes – rapid growth leading to IPO or acquisition, collapse and disappearance, or struggling to survive. If a project only belongs to one company, customers will worry whether the company will stop maintaining it or switch to proprietary. After donating to a foundation, even if the company is no longer around, the code remains with the foundation, ensuring sustainability.

Of course, not all foundations have sufficient governance capabilities, which also needs to be considered. Additionally, there are ways to operate without donating to a foundation. For example, MinIO, a storage-related project, was not donated to a foundation. Later, it made some moves that the community considered "questionable operations" – no longer maintaining some older versions, removing some pre-built images, and planning to change the license. From a business perspective, after casting the net, it's time to reel it in, which is MinIO's way of being responsible to its shareholders (maximizing profit). But from a community perspective, people started looking for alternative projects, and several MinIO alternatives saw their Star counts skyrocket.

So, if an open source project wants to go global, it's best to find its benchmark – either an open source alternative to a proprietary product, or a better, upgraded version of existing open source products. Being brave enough to benchmark against competitors is crucial for potential users to recognize you, then potentially endorse you, and finally establish yourself in the global market. I've digressed a bit, but returning to the topic of foundations, donating to a foundation indeed offers many benefits, but whether or not to donate ultimately depends on the company's business model and target users.

How to choose whether to join a foundation?

Monica

Is joining a leading foundation a very good path for startups going global?

Richard

I think it's a viable path, but whether it's "very good" depends on whether your company and users prioritize the project's long-term sustainability. Which users care about this? Primarily enterprise users who incorporate your software into their software supply chain (i.e., the "SBOM" list, Software Bill of Materials). Just as hardware is broken down into components, software also has its "bill of materials." The quality and sustainability of upstream software directly affect downstream products. If your project is entering the B2B sector, enterprise users will definitely pay attention to these issues, because stability is paramount in the B2B industry.

However, if your software is consumer-facing (B2C), the situation is different. End-users don't care whether you've donated to a foundation; as long as the code is freely available and works properly, they don't even care if it's "open source." The core of open source is "having code + a compliant license," but some projects just put code on GitHub without any license and still become popular because they meet users' core needs.

So, for B2C projects or projects that don't enter a serious software supply chain, there's no need to agonize over donating to a foundation in the early stages. The focus should be on achieving product-market fit (PMF) first. If the product is well-made and easy to use, it can spread even with a non-standard open source license or no license at all. If the product isn't good, even if it's donated to a foundation, no one will want to use it.

For example, Dify is a successful case of Chinese open source going global last year. They use a non-standard open source license and haven't donated to a foundation, but they are still very popular. Their benchmark is the German N8N project, which also uses a non-standard license and is equally successful. This shows that whether the license is standard or whether it's donated to a foundation is not the decisive factor for a project's success; the core is PMF.

Monica

Is the barrier to joining a foundation high?

Richard

The barrier to joining a foundation mainly depends on the specific foundation's requirements, with two core points:

First is the cost. Many foundations (such as the Linux Foundation, Eclipse Foundation) operate on a membership model, relying on corporate membership fees to support the foundation's daily operations and project ecosystem development. However, others, like the Apache Software Foundation, adopt a different model. It does not have a corporate membership system, nor does it require payment as a prerequisite for participation or governance. Instead, it focuses on individual contributions, emphasizing community governance, continuous contribution, and the inherent health of the project itself.

Second is the project's alignment with the foundation and the groundwork laid through prior communication. You can't just apply to any foundation; you need to first understand the foundation's direction – for example, some foundations specialize in AI and only accept AI-related projects; some foundations might already have similar projects and won't accept duplicates (but ASF is not like this, it still depends on the specific foundation's judgment). In some foundations (especially industry-specific, membership-based foundations), early communication and consensus building are very important.

In practice, having a "guide" who is familiar with the foundation's culture and processes is very important. Such individuals usually have a deep understanding of how the foundation operates, what review criteria they focus on, and common risks, which can help projects avoid detours during the preparation phase.

This support mostly manifests as experience sharing, process guidance, and governance advice, rather than interference with the outcome. Even in open source foundations that emphasize transparency and open decision-making, trust and long-term collaborative experience still hold value.

Such guides can be friends helping out, or you can privately find the right people for paid consulting – after all, many foundation members may have other jobs and cannot spend a lot of time guiding you for free.

As a business organization, efficiency is key. If you have connections, use them; if not, use consulting services to quickly understand the correct procedures and approaches in the open source world. Of course, regardless of the open source foundation, formal decisions must be made through public processes, not through the old-fashioned "backroom deals" common in traditional industries.

Richard

Haha, I suppose I am. Because I have a certain degree of connection with people from various foundations, but I'm not omnipotent. For example, if someone comes to me for advice, I might be familiar with someone at a particular foundation, but I might not know the technical committee members responsible for specific project types within that foundation. Actually, in an ideal open source community, there shouldn't be a "guide" role – if a project is good, it should be approved upon application. But in reality, many teams don't understand open source rules, and their projects don't meet foundation requirements. Blindly applying will only lead to failure, wasting time and effort. In these situations, professional guidance can increase the success rate.

Speaking of which, I'd like to recommend two books. This isn't a sales pitch, as I only received a one-time translation fee for these books; I don't earn more if more copies are sold. One is "The Open Source Way," published by Posts & Telecom Press in 2025. This book helps people understand how healthy open source projects operate; the content is comprehensive, and even those unfamiliar with open source can understand it. The other is "Developer Relations: Methods and Practices," also published by Posts & Telecom Press, and also translated by me.

The reason I translated these two books is that there are too few high-quality open source-related books in the Chinese world. A decade ago, when I worked in Taiwan, I translated overseas open source articles into Chinese and shared them, and now I'm continuing that work. However, I want to remind everyone that even with guides and book guidance, the core of project success still lies with the team itself – whether your mindset and collaboration model truly align with open source culture.

Many domestic teams' engineers have coding habits that are incompatible with open source culture. For example, they don't know how to use Issues and PRs (Pull Requests) for standardized communication, and their code submissions lack detailed annotations and documentation, making it difficult for others to contribute. I've coached some teams and found that many engineers don't have a language problem (although PRs should be written in English), but rather a severe lack of communication skills – they are accustomed to writing code that just runs, without valuing documentation and collaboration, which is unacceptable in the open source community.

The success of an open source project requires not only good code but also clear annotations, comprehensive documentation, and an open communication attitude. External users or developers will judge the quality of your project and the professionalism of your team through details like code, Issues, and PRs, and then decide whether to use or contribute.

When I worked at Huawei, I noticed that much internal communication happened via phone calls and instant messages, without written records. When problems arose, leaders would dictate what to do. Over time, everyone's ability for standardized communication deteriorated. This engineering culture clashes with open source culture. Many domestic teams going global feel good about themselves, but in the eyes of overseas developers, they might appear "clownish" because their collaboration methods and communication habits don't conform to open source community norms. Many teams are still unaware of this.

How to commercialize open source going global?

Monica

After an open source project goes global, what are the typical business models? How does commercialization begin, and how does it make money?

Richard

In 2025, I probably gave no less than ten public or private talks on "open source commercialization." Actually, I don't really like the term "open source commercialization" – why does no one ask "how to commercialize proprietary software"? Because the core issue isn't "open source," but "software commercialization." Open source is just a form of software delivery and distribution, similar to selling proprietary software on discs or as cloud services; it's just a different delivery method.

The essence of software commercialization is product-market fit. Whether it's open source or proprietary, the core logic is the same. It's just that with open source, the code is publicly available for free, making people think it's hard to make money, which is why they specifically ask "how to commercialize open source."

The main ways open source projects generate revenue are:

The first type is open source basic version + commercial paid version. The open source version addresses users' basic needs, attracting a large number of free users and establishing market mindshare; the commercial version offers more advanced features and exclusive services, targeting commercial users and enterprises willing to pay. The core of this model is to forgo the long-tail free market in exchange for brand awareness, user trust, and commercial conversion opportunities.

The second type is plugin ecosystem monetization. The open source project serves as a foundational platform, allowing third-party developers to create paid plugins based on it. For example, WordPress is an open source platform that is free itself, but various plugins on it (like paid themes, functional plugins) can make money, much like an app store. The platform provides traffic, plugin developers earn money, and the platform can also take a cut.

The third type is professional service fees. This is Red Hat's classic model. Red Hat packages Linux into distributions (like Fedora, CentOS), providing them to users for free, and then offers technical support, customized development, training, and other professional services to enterprise users. This model is very popular in European and American markets because overseas companies have high labor costs and are willing to pay for professional services rather than building their own teams to solve problems.

However, this model is difficult to implement in China. Chinese companies are more accustomed to hiring their own people to solve problems, feeling that paying for services is less cost-effective than hiring staff, and that external services are not customized enough to meet their needs. Just like many companies using outsourcing often have conflicts with outsourced teams, they prefer their own employees. So, Chinese companies prefer to spend money on staffing rather than paying open source service providers, which is related to China's labor cost structure and corporate culture.

The fourth type is capital exit. Some open source projects grow rapidly through financing and are then acquired by large companies, realizing profitability. In this model, overseas capital values open source projects more highly because they recognize the core value of the technology. The US capital market developed early, and the VC industry is mature, with many investors willing to invest in open source projects with technological barriers. Chinese capital, on the other hand, focuses more on safety margins and has a less deep understanding of open source technology. Many past investments in SaaS have resulted in losses, so investment in open source projects is relatively cautious.

However, there's a shift in the capital market now: previously, just having an idea and a seemingly good project could secure funding; now, capital places more emphasis on user adoption and PMF, and will no longer spend money letting you slowly find your direction. If your open source project is growing rapidly in users, it indicates PMF has been achieved, making financing relatively easier. But if growth slows, you need to communicate clearly with investors whether the niche is saturated or if there's a problem with the development strategy, and then formulate a commercialization path.

How to tell a good story and enhance value?

Monica

After an open source project goes global, how can it increase its value and tell its story well in the eyes of users and investors?

Richard

Actually, telling a good story for an open source project has many commonalities with proprietary projects, but open source has a more significant communication advantage – you don't need to spend a lot of time convincing customers to try it. The open source code is there; people can download and use it directly, making it easier to gain initial trust.

First, it's important to clarify that open source itself is a huge "selling point." You don't need to be better than proprietary products; just being open source already gives you a differentiated advantage. For example, for B2B projects, open source allows enterprise users to freely try and verify its effectiveness, which is simpler than the "trial application" process for proprietary products, and makes it easier to be included in the software supply chain.

Second, distinguish whether the target users are B2B or B2C; the narrative logic differs:

If it's a B2B project, the core is to "occupy an ecological niche." You need to gain recognition from industry insiders and become "one of the options" in a specific vertical. For example, open source large models need to compete on authoritative leaderboards (like LMArena, which is led by Chinese scholars at Berkeley and recently raised $150 million in Series A funding) to prove their strength with objective data. They also need to gain recognition from third-party communities (like Hugging Face, ModelScope) and academia – publishing high-quality papers and getting endorsements from industry experts are key to increasing value.

When I was at 01.AI, I often said at industry events that the three best open source large models in China at the time were Qwen, DeepSeek, and 01.AI's Yi model. Why these three? Because they performed best on authoritative leaderboards and had practical ecosystem applications. At that time, DeepSeek was very low-key, and outsiders hadn't heard of it, but it already had high recognition within the industry. Later, DeepSeek exploded in popularity because it excelled in inference, occupying that ecological niche. Even if other stronger models emerged later, DeepSeek remained the benchmark in people's minds, with some even using other models for secondary development and claiming they were based on DeepSeek.

If it's a B2C project, the core is "user operations." Like a fan economy, you need to build a user group, encouraging users to actively spread the word and share use cases. For example, Midjourney attracted a large number of users through Discord community operations in its early days. Open source projects are the same: you need users to be willing to share their usage experience and secondary development results, creating word-of-mouth spread.

If it's a project that can be both B2C and B2B (like Dify, N8N), the narrative logic is "B2C for mindshare, B2B for monetization." C-end users use it for free, building widespread brand recognition; B-end users commercialize after secondary development, sharing revenue with the original project owner according to the agreement. This model is both "critically acclaimed and commercially successful," having both reputation and income, which investors also highly recognize.

For investors, the core metrics for evaluating open source projects are: user adoption (how many people use it), ecosystem diversity (are there external contributors), and commercial conversion efficiency (can it make money). You need to prove to investors that your project not only has free users but also commercial customers willing to pay; and that it's not just maintained by your own team but also has external developers contributing. Such a project has long-term value.

It's also important to note that the narrative for open source projects must align with overseas cognitive logic. Overseas users and capital value transparency and community openness more. You need to demonstrate the project's governance structure and collaboration model, making them feel that it is a healthy, sustainable open source project, not a "pseudo-open source" project controlled by a single company.

How to value open source projects?

Monica

How are open source projects valued? It seems that conventional methods like PS (Price-to-Sales Ratio) are not quite suitable?

Richard

The valuation of open source projects primarily relies on "benchmarking" and "ecological niche value." Conventional methods like PS (Price-to-Sales Ratio) and PE (Price-to-Earnings Ratio) are indeed not entirely applicable because many open source projects have no revenue in their early stages but possess high ecological value.

If there are overseas benchmark projects, the valuation can refer to the logic of those benchmark projects. For example, PingCAP's TiDB project has similar open source database companies overseas. PingCAP's valuation was determined by referencing the development stage, ecological niche, and user scale of these companies. Although some people think PingCAP's last round of financing had a high valuation, if its ecological niche story can be realized, there is still room for its valuation to grow.

Another example is MySQL. It's an open source database developed by a Swedish company, which later became a core component of the LAMP stack (Linux+Apache+MySQL+PHP). In the early days of website development, almost everyone used these four components, of which only MySQL was owned by a company, while the other three were foundation projects. By occupying this ecological niche, MySQL was eventually acquired by Oracle at a high price. This can be seen as a "defensive acquisition," and its valuation was based on the indispensability of its ecological niche; if Oracle hadn't bought it, it would have continued to erode the mid-to-low-end database market.

If there are no direct benchmark projects, the valuation depends on the capital's perception and narrative ability. There's a significant difference in valuation logic between USD capital and RMB capital:

USD capital has a more mature understanding of open source technology. They recognize the value of the technology itself and are willing to pay a premium for projects with clear ecological niches and rapid user growth. For example, many VCs in the US specialize in open source; their partners are often from the open source community themselves, understanding technology and ecosystems, and capable of seeing the long-term value of projects.

RMB capital is more focused on safety margins, preferring to invest in projects that already have revenue and clear business models, and lacking a deep understanding of the ecological value of open source projects. Moreover, the exit paths for domestic capital markets are relatively singular – either domestic IPOs or acquisitions by domestic companies. Both methods lead to relatively conservative valuations for open source projects, making it difficult to reach the valuation levels seen in overseas markets.

Another important point: the valuation of an open source project is inversely proportional to its "substitutability." If your project is irreplaceable in a certain ecological niche, even if its revenue is not high, its valuation will be high. If there are many alternative projects, even if the revenue is good, the valuation will be affected. For example, Tabular, the company behind the Apache Iceberg project, had an annual revenue of only $1 million, but its position in the big data ecosystem was irreplaceable, allowing it to be acquired at a high price.

There's also a current trend in the capital market: more and more open source projects are being acquired by strategic investors, and fewer are going public. This is because acquisition offers a faster and more certain exit path for both capital and teams – capital can quickly retrieve returns, and team members, though possibly bound for 4 years, also receive stable compensation.

Open source projects in the Chinese market

Monica

Some domestic open source projects choose not to go global, focusing only on the Chinese market. What's your view on this path?

Richard

The Chinese market itself is vast, and there are indeed opportunities to make money, but the business model differs from projects that go global. For these open source projects focused solely on the domestic market, the core logic is "open source for customer acquisition + proprietary/service monetization" – using open source code to attract potential customers, and then earning revenue through commercial versions, professional services, or SaaS services.

Such projects typically have several characteristics:

First, they receive RMB financing, and the investors' exit path is a domestic IPO or acquisition by a domestic enterprise. Therefore, these projects are required to first establish a firm foothold in China and generate stable cash flow. Domestic capital places more emphasis on revenue and profit, unlike USD capital, which is willing to wait longer for ecosystem maturity.

Second, the products are "large and comprehensive," meeting the one-stop needs of large domestic enterprises. Overseas open source projects are mostly "small and exquisite," focusing on a specific vertical. However, domestic projects serving large enterprises need to provide complete solutions. For example, Huawei's products, while not necessarily top-tier in every single technology, offer strong overall solution capabilities that make customers "worry-free," which is also a core competitive advantage.

Third, open source is merely a means of customer acquisition; core profitability still relies on traditional B2B services. Large domestic enterprises value service quality and customization capabilities more. Open source projects use free code to let customers understand the product, then sales and BD teams follow up, providing customized development, technical support, and other services to ultimately achieve monetization. Some projects even boost performance through "order swapping," for example, I have customer resources, you have project resources, we cooperate to increase turnover, preparing for an IPO.

This path is viable, as there is a large unmet demand from enterprises in China. However, it's important to note that the Chinese market is increasingly demanding compliance with open source regulations. 开源项目与基金会的关系

Monica

嗯，首先恭喜 Richard 找到一个非常不错的平台。这里我有个问题想请教：开源组织把项目捐给美国的基金会后，和基金会是什么关系？包括所有权归属、未来发展这些方面，能不能详细说说？

Richard

首先得明确几个核心概念：开源项目、开源授权、项目捐献，这三者是不一样的。先说说著作权和所有权 —— 不管是公司还是个人，开发出一个软件作品，从著作权法的角度来说，就天然拥有这个作品的著作权。就像以前卖音乐、卖版权一样，你创作了一个东西，就享有相应的权利。有些地方需要登记，比如中国要登记软件著作权，美国要在国会图书馆登记，但不管登不登记，著作权本身是存在的。

拥有著作权之后，你有很多选择：可以闭源卖钱，可以免费赠送，也可以通过开源的方式授权给别人使用。这里要注意，开源的核心是 “授权（open source licensing）”，就像 IP 授权一样 —— 我把使用权利授权给你，但所有权（ownership）还是在我手里，我只是把部分权利许可给你使用而已。

开源授权也是这个逻辑：我作为著作权所有人，通过一个开源协议，把项目代码放到 GitHub 等平台上，任何人都可以查看和使用。只要是正规的 GitHub 项目，在 README 文件里一定会写明使用的开源协议，根目录下也会有一个 LICENSE.TXT 文件，明确标注是哪一种开源协议。因为全球有很多种标准的开源协议，这些协议都由一个叫 OSI（Open Source Initiative，开源促进会）的组织管理。你自己发明一个开源协议不算数，必须提交给 OSI 审核，通过之后才能被称为 “OSI 批准的标准开源协议”。当然也有非标的开源协议，比如 Dify，他们就是基于标准协议修改的，添加了一些商业保护性条款。

常见的标准开源协议有 Apache 2.0（就是我们公司项目捐献的 Apache 基金会相关协议）、GPL（和自由软件基金会相关，Linux 内核用的就是这个协议）、MIT（源自麻省理工学院）、BSD（源自伯克利软件发行版），全球大概有上百种这样的标准协议。

现在回到你的问题：开源授权和把项目捐给基金会是两回事。如果一家公司只是把项目开源，没有捐献基金会，那么项目的所有权还是属于这家公司的。开源协议只是规定了别人使用这个项目的 “游戏规则”—— 比如你可以免费使用、二次开发，但如果二次开发后要商业化售卖，必须告诉你的客户，这个产品是基于哪个上游开源项目做的，要把声誉归还给原作者；同时，如果你二次开发的产品出了问题，客户不能找原作者追责，因为开源是免费授权，原作者不承担产品瑕疵担保责任。

举个例子，如果你用了我的开源软件做二次开发，然后卖给客户，客户用着出了问题，那应该找你负责，而不是找我。这和食品供应链不一样 —— 如果你的预制菜用了我的原料，吃出问题可能是我的责任，但开源软件不一样，除非能证明原作者是故意 “开源投毒”（在代码里埋恶意程序），否则原作者不需要为瑕疵负责，因为软件是免费提供的。

再说说把项目捐给基金会。全球最知名的两个开源基金会是 Linux 基金会和 Apache 软件基金会。为什么要把项目捐出去？核心是为了让用户相信项目的长期可持续性。有些开源项目属于某家公司，后期可能会修改协议、闭源收费，就像让用户 “吃鸦片上瘾” 之后再收割，这种做法虽然合法，但会损害社区信任。而捐给基金会之后，项目就不会被随意闭源或修改协议，就算捐献的公司倒闭了，基金会还可能找人接手维护，项目依然能继续发展。

我们公司的 Gravitino 项目捐给 Apache 基金会，就是为了让全球客户放心。对于任何初创公司都是一样的，结局无非三种：快速发展上市或被收购、倒闭消失、勉强苦撑。如果项目只属于某家公司，客户会担心公司是否不维护或改闭源；捐给基金会之后，就算公司不在了，代码还在基金会，可持续性有了保障。

当然，不是所有基金会都有足够的治理能力，这也是需要考虑的。另外，不捐基金会也有不捐的玩法，比如存储相关的项目 MinIO，它就没有捐给基金会，后期做了一些被社区认为是 “骚操作” 的事情 —— 不再维护部分旧版本、撤掉一些打包好的镜像，还打算修改协议。站在商业角度，撒网之后开始收网，这是 MinIO 对股东负责（创造利润最大化）的做法；但站在社区角度，大家就会去找替代项目，当时有好几个 MinIO 的平替项目，Star 数量蹭蹭往上涨。

所以如果开源项目想全球化出海，最好要找到自己的对标 —— 要么是闭源产品的开源平替，要么是比现有开源产品更好的升级版本，勇于和竞品对标，才能让潜在用户认知到你，进一步才可能认可你，让你在全球市场站稳脚跟。扯远了，回到基金会的话题，捐献基金会的好处确实很多，但具体要不要捐，还是要看企业的商业模式和目标用户。

如何选择是否要加入基金会？

Monica

加入头部基金会对初创企业出海来说，是一个非常好的路径吗？

Richard

我觉得是一个可行的路径，但算不算 “非常好”，要看你的企业和用户是否关注项目的长期可持续性。哪些用户会关注这个问题呢？主要是那些把你的软件纳入他们的软件供应链（也就是所谓的 “SBOM” 表，软件物料清单）的企业用户。就像硬件要拆分成零件一样，软件也有自己的 “物料清单”，上游软件的质量、可持续性会直接影响下游产品。如果你的项目要进入 ToB 领域，企业用户一定会关注这些问题，因为 ToB 行业最看重稳定性。

但如果你的软件是面向终端用户（ToC）的，情况就不一样了。终端用户根本不关心你有没有捐基金会，只要代码能免费获取、能正常使用就行，他们甚至都不会在意你是不是 “开源”—— 开源的核心是 “有代码 + 有合规协议”，但有些项目只把代码放到 GitHub 上，没有任何协议，照样能火，因为它满足了用户的核心需求。

所以对于 ToC 项目或者不进入严肃软件供应链的项目来说，初期不用纠结于捐基金会，重点是先实现产品与市场的匹配（PMF）。产品做得好用，就算是非标开源协议，甚至没有协议，也能传播开来；产品不好用，就算捐了基金会，也没人愿意用。

举个例子，Dify 是去年中国开源出海的成功案例，他们用的就是非标开源协议，没有捐给基金会，但照样很火。他们的对标是德国的 N8N 项目，N8N 用的也是非标协议，同样很成功。这说明协议是否标准、是否捐基金会，并不是项目成功的决定性因素，核心还是 PMF。

Monica

加入基金会的门槛高吗？

Richard

加入基金会的门槛主要看具体基金会的要求，核心有两点：

第一是费用。许多基金会（如 Linux 基金会、Eclipse 基金会）采用会员制运作，通过企业缴纳会费来支持基金会的日常运营与项目生态建设。但也有例如Apache 软件基金会则采取不同模式，它不设企业会员制度，也不以缴费作为参与或治理的前提，而是以个人贡献为核心，强调社区治理、持续贡献与项目自身的健康度。

第二是项目与基金会的契合度，以及前期的沟通铺垫。你不能随便找个基金会就申请，得先了解基金会的发展方向 —— 比如有些基金会专注 AI 领域，只接纳 AI 相关项目；有些基金会可能已经有类似的项目了，就不会再接受重复项目（但ASF不是这样，还是要看具体基金会判断）。在一些基金会（尤其是产业型、会员制基金会）中，前期沟通和共识建立非常重要。

在实际操作中，拥有熟悉基金会文化与流程的“指路人”非常重要。这类人士通常对基金会的运作方式、评审关注点以及常见风险非常了解，能够帮助项目在准备阶段少走弯路。

这些支持多数体现为经验分享、流程辅导和治理建议，而非对结果的干预。即便在强调透明和公开决策的开源基金会中，信任与长期协作经验依然有价值。

这种指路人，有些是朋友间的帮忙，有些也可以私下找到对的人来付费咨询 —— 毕竟不少基金会成员本身可能有其他工作，不可能免费花大量时间指导你。

作为商业组织，要讲究效率，有关系就运用，没关系就通过顾问服务，尽快搞清楚什么才是在开源世界中正确的流程和姿势。当然，不管是什么开源基金会，基金会的正式决策仍必须通过公开流程完成，不可能是传统产业那种打通关系暗箱操作的老套路。

Monica

你算是这种指路人吗？

Richard

哈哈，我应该算是吧。因为我和各个基金会的人都有一定程度的链接，但也不是万能的。比如有人来请教我，我可能和某个基金会的人熟，但不一定认识这个基金会里负责特定项目类型的技术委员会成员。这时候我会帮他牵线搭桥，先和基金会的人简单沟通，了解他们的审核逻辑和发展目标，再反馈给企业。

基金会也会私下了解我和项目方的关系，是单纯的朋友介绍，还是我担任了项目的顾问，这些都会影响他们对项目的态度。

其实在理想的开源社区里，不应该有 “指路人” 这种角色 —— 项目只要做得好，提交申请就能通过。但现实中，很多团队对开源规则不了解，做出来的项目不符合基金会要求，盲目申请只会失败，浪费时间和精力。这时候有专业的人指导，能提高成功率。

说到这里，我想推荐两本书，不算带货，因为我翻译这两本书只拿了一次性翻译费，多卖一本我也不会多赚钱。一本是《开源项目成功之道》，2025 年由人民邮电出版社出版，这本书能让大家了解健康的开源项目是怎么运作的，内容很全面，不懂开源的人也能看懂；另一本是《开发者关系：方法与实践》，也是人邮出版的，同样是我翻译的。

我之所以翻译这两本书，是因为中文世界里优质的开源相关书籍太少了。十几年前我在台湾工作时，就是把海外的开源文章翻译成中文分享出去，现在算是延续了这个工作。不过要提醒大家，就算有指路人、有书籍指导，项目成功的核心还是团队本身 —— 你们的思维方式、协作模式是不是真的符合开源文化。

很多国内团队的工程师，写代码的习惯和开源文化格格不入。比如不知道怎么用 Issue、PR (Pull Request) 做规范沟通，代码提交后没有详细注解和文档，别人想参与贡献都不知道从哪里入手。我辅导过一些团队，发现很多工程师不是语言问题（虽然 PR 都要用英文写），而是沟通能力太差 —— 他们习惯了写完代码能跑就行，不重视文档和协作，这在开源社区是行不通的。

开源项目的成功，不仅需要好代码，还需要清晰的注解、完善的文档，以及开放的沟通态度。外部用户或开发者看你的项目，会通过代码、Issue、PR 这些细节判断项目的质量和团队的专业性，进而决定要不要使用或贡献。

我在华为工作时就发现，很多内部沟通都是通过电话、即时消息，没有书面记录，遇到问题领导说怎么干就怎么干，长期下来，大家的规范沟通能力变得很差。这种工程师文化和开源文化是冲突的，很多国内团队出海，自我感觉良好，但在海外开发者眼里，可能就是 “小丑”，因为他们的协作方式和沟通习惯不符合开源社区的规范。这一点，很多团队自己还意识不到。

开源出海如何商业化？

Monica

开源项目出海后，商业模式一般是怎样的？怎么开始商业化、怎么赚钱？

Richard

2025 年这一年，我大概做了不下十场关于 “开源商业化” 的公开或闭门分享。其实我不太喜欢 “开源商业化” 这个说法 —— 为什么没人问 “闭源怎么商业化”？因为核心问题不是 “开源”，而是 “软件商业化”。开源只是软件的交付和分发形式，和闭源卖光盘、云化服务一样，只是交付方式不同而已。

软件商业化的本质是产品与市场的匹配，不管是开源还是闭源，核心逻辑都是一样的。只不过开源是免费公开代码，大家觉得不好赚钱，才会专门问 “开源怎么商业化”。

开源项目的盈利方式主要有这几种：

第一种是基础版开源 + 商业版收费。开源版本解决用户的基础需求，吸引大量免费用户，占据市场心智；商业版本提供更高级的功能、专属服务，针对有付费意愿的商业用户和企业用户收费。这种模式的核心是，放弃中长尾免费市场，换取品牌知名度、用户信任和商业转化机会。

第二种是插件生态盈利。开源项目作为基础平台，允许第三方开发者基于平台开发付费插件。比如 WordPress 是开源平台，本身免费，但上面的各种插件（如付费主题、功能插件）可以赚钱，就像应用商店一样，平台提供流量，插件开发者赚钱，平台也能从中分成。

第三种是专业服务收费。这是 Red Hat 的经典模式，Red Hat 把 Linux 做成发行版本（如 Fedora、CentOS），免费提供给用户使用，然后针对企业用户提供技术支持、定制化开发、培训等专业服务。这种模式在欧美市场很受欢迎，因为海外企业人力成本高，宁愿花钱买专业服务，也不愿意自己组建团队解决问题。

但在国内，这种模式很难走通。国内企业更习惯自己养人解决问题，觉得花钱买服务不如自己招人划算，而且觉得外部服务不够定制化，不符合自己的需求。就像很多公司用外包，经常会和外包团队产生矛盾，不如自己员工听话。所以国内企业宁愿把钱花在养人上，也不愿意付给开源服务厂商，这和国内的人力成本结构、企业文化都有关系。

第四种是资本退出。有些开源项目通过融资快速发展，然后被大公司收购，实现盈利。这种模式下，海外资本对开源项目的估值更高，因为他们更认可技术的核心价值。美国的资本市场发展早，VC 行业成熟，很多资本愿意投资有技术壁垒的开源项目；而国内资本更关注安全边际，对开源技术的认知不够深，过去投资 SaaS 的很多都亏了，所以对开源项目的投资相对谨慎。

不过现在资本市场有个变化：以前只要有个想法、项目看起来不错，就能融到钱；现在资本更看重用户采纳度（adoption）和 PMF，不会再花钱让你慢慢找方向。如果你的开源项目用户增长很快，说明已经达到 PMF，融资会相对容易；但如果增长放缓，就要和资本沟通清楚，是生态位已经饱和，还是发展策略有问题，再制定商业化路径。

如何讲好故事和提升价值？

Monica

开源项目出海后，怎么在用户和投资人眼中提高身价，讲好自己的故事？

Richard

其实开源项目讲好故事，和闭源项目有很多共通之处，但开源的传播优势更明显 —— 你不用花大量时间说服客户试用，开源代码放在那里，别人可以直接下载使用，更容易获得初始信任。

首先要明确，开源本身就是一个很大的 “卖点”。你不需要做得比闭源产品更好，只要开源，就已经有了差异化优势。比如 ToB 项目，开源让企业用户可以自由试用、验证效果，比闭源产品的 “试用申请” 流程更简单，更容易被纳入软件供应链。

其次，要分清楚目标用户是 ToB 还是 ToC，叙事逻辑不一样：

如果是 ToB 项目，核心是 “占领生态位”。你要让行业内的人认可你，成为某个垂直领域的 “选项之一”。比如开源大模型，要去打权威榜单（如 LMArena，这个榜单由伯克利华人学者牵头做的，最近 A 轮还融了 1.5 亿美元），用客观数据证明自己的实力；还要让第三方社区（如 Hugging Face、魔搭社区）、学术圈认可你 —— 发表高质量论文，让行业专家背书，这些都是提高身价的关键。

我以前在零一万物的时候，经常在行业活动中说，当时中国最好的三个开源大模型是千问、DeepSeek 和零一万物Yi模型。为什么是这三个？因为它们在权威榜单上的表现最好，而且有实际的生态应用。当时 DeepSeek 还很低调，行外人都没听过，但在行业内已经有了很高的认可度。后来 DeepSeek 爆火，就是因为它在推理领域做得特别好，占领了这个生态位，就算后来有其他更强的模型出来，大家的心智里还是觉得 DeepSeek 是标杆，甚至有人用其他模型做二次开发，对外还说是基于 DeepSeek 的。

如果是 ToC 项目，核心是 “用户运营”。就像粉丝经济一样，要建立用户群体（User Group），让用户主动传播、分享使用案例。比如 Midjourney 早期通过 Discord 社区运营，吸引了大量用户；开源项目也一样，要让用户愿意分享自己的使用体验、二次开发成果，形成口碑传播。

如果是既能 ToC 又能 ToB 的项目（比如 Dify、N8N），叙事逻辑就是 “ToC 建心智，ToB 做变现”。C 端用户免费使用，形成广泛的品牌认知；B 端用户二次开发后商业化，按照协议向原项目方分成。这种模式 “叫好又叫座”，既有口碑又有收入，投资人也很认可。

对投资人来说，评估开源项目的核心指标是：用户采纳度（有多少人用）、生态多样性（有没有外部贡献者）、商业转化效率（能不能赚钱）。你要向投资人证明，你的项目不仅有免费用户，还有愿意付费的商业客户；不仅有自己团队在维护，还有外部开发者参与贡献，这样的项目才具有长期价值。

还要注意，开源项目的叙事要符合海外的认知逻辑。海外用户和资本更看重透明性、社区开放性，你要展现出项目的治理结构、协作模式，让他们觉得这是一个健康、可持续的开源项目，而不是一家公司控制的 “伪开源” 项目。

开源项目如何估值？

Monica

开源项目的估值怎么算？好像不太适合用常规的 PS (Price-to-Sales Ratio，市销率) 之类的方法？

Richard

开源项目的估值，核心是 “对标” 和 “生态位价值”，常规的 PS、PE (Price-to-Earnings Ratio，市盈率) 方法确实不完全适用，因为很多开源项目早期没有收入，但生态价值很高。

如果有海外对标项目，估值就可以参考对标项目的逻辑。比如 PingCAP 的 TiDB 项目，海外有类似的开源数据库公司，PingCAP 的估值就是参考了这些公司的发展阶段、生态位、用户规模来定的。虽然有人觉得 PingCAP 最后一轮融资估值高，但如果它的生态位故事能实现，估值还有上升空间。

再比如 MySQL，它是一家瑞典公司开发的开源数据库，后来成为 LAMP 生态（Linux+Apache+MySQL+PHP）的核心组件 —— 早期做网站，几乎都要用这四件套，其中只有 MySQL 是公司所有，其他三个都是基金会项目。MySQL 通过占领这个生态位，最后被 Oracle 高价收购，可以说是一种 “防御性收购”，它的估值就是基于生态位的不可替代性来的；如果 Oracle 不买，它将继续蚕食中低端数据库市场。

如果没有直接对标项目，估值就看资本的认知和叙事能力。美元资本和人民币资本的估值逻辑差异很大：

美元资本对开源技术的认知更成熟，他们认可技术本身的价值，愿意为生态位清晰、用户增长快的项目支付溢价。比如美国有很多专注开源的 VC，他们的合伙人本身就是开源圈的人，懂技术、懂生态，能看到项目的长期价值。

人民币资本更关注安全边际，喜欢投已经有收入、商业模式清晰的项目，对开源项目的生态价值认知不足。而且国内资本市场的退出路径相对单一，要么国内上市，要么被国内公司收购，这两种方式对开源项目的估值都相对保守，很难达到海外市场的估值水平。

还有一个点很重要：开源项目的估值和它的 “可替代性” 成反比。如果你的项目在某个生态位里是不可替代的，就算收入不高，估值也会很高；如果有很多替代项目，就算收入不错，估值也会受影响。比如主导 Apache Iceberg 项目的 Tabular 公司，一年收入只有 100 万美元，但它在大数据生态里的位置不可替代，所以能被高价收购。

现在资本市场还有个趋势：开源项目被产业资本收购的案例越来越多，上市的案例越来越少。因为被收购对资本和团队来说，都是更快速、更确定的退出方式 —— 资本能快速拿回收益，团队成员虽然可能被绑定 4 年，但也能获得稳定的回报。

中国市场的开源项目

Monica

国内有些开源项目选择不出海，只做中国市场，怎么看这种路径？

Richard

中国市场本身很大，不是没有赚钱的机会，只是商业模式和出海项目不一样。这些只做国内市场的开源项目，核心逻辑是 “开源获客 + 闭源 / 服务变现”—— 用开源代码吸引潜在客户，然后通过商业版本、专业服务、SaaS 服务赚钱。

这类项目通常有几个特点：

第一，拿到的是人民币融资，投资方的退出路径是国内上市或被国内企业收购，所以要求项目先在国内站稳脚跟，形成稳定的现金流。国内资本更看重营收和利润，不像美元资本那样愿意长期等待生态成熟。

第二，产品 “大而全”，满足国内大企业的一站式需求。海外开源项目大多是 “小而精”，聚焦某个垂直领域；而国内项目要服务大企业，需要提供完整的解决方案，比如华为的产品，虽然单项技术不一定是全球顶尖，但整体解决方案能力强，能让客户 “省心”，这也是一种核心竞争力。

第三，开源只是获客手段，核心盈利还是靠传统的 ToB 服务。国内大企业更看重服务质量和定制化能力，开源项目通过免费代码让客户了解产品，然后派销售、BD 团队跟进，提供定制化开发、技术支持等服务，最终实现变现。有些项目甚至会通过 “换单” 的方式做业绩，比如我有客户资源，你有项目资源，我们互相合作，把营业额做起来，为上市做准备。

这种路径本身是可行的，毕竟国内有大量未被满足的企业需求。但要注意，国内市场对开源合规性的要求越来越高，就算不出海，也要遵守开源协议，规范项目治理，否则可能会引发法律风险或社区信任危机。

Monica

中国开源项目出海成功的案例很少，核心问题出在哪里？是产品不够硬，还是叙事没讲好，或者是合规和信任问题？

Richard

首先要明确：不是没有华人主导的开源出海成功案例，只是国内土生土长的项目成功案例少。我认识一个大陆出生的华人，在美国已经成功卖出了两三家开源公司，都是他自己创业做的，很低调，只有行业内的人知道。这种 “个人出海 + 海外创业” 的模式，天然契合海外市场的规则和文化，成功概率更高。

国内土生土长的项目出海难，核心是三个问题叠加：

第一是合规与信任问题。海外市场对开源项目的著作权、协议合规性、数据安全、创始人背景等要求很高。比如有些项目因为创始人是中国国籍，海外客户会担心数据安全；有些项目的开源协议不合规，被海外社区质疑是 “伪开源”；还有些项目在著作权归属上有争议，影响客户信任。

有些项目为了规避这些问题，会选择 “拆分模式”—— 把公司拆成美国公司和中国公司，项目版本也分开，各自对接本地资本和市场。这种模式虽然麻烦，但能降低合规风险，提高海外客户的信任度，我知道有几个项目这么做之后，出海进程明显加快了。

第二是文化与叙事差异。国内团队的运作模式、工程师文化和开源文化有差距。比如国内团队习惯封闭研发，不重视社区运营；工程师沟通能力不足，不擅长用 Issue、PR 做规范协作；叙事方式也不符合海外受众的认知 —— 海外更看重技术透明性、社区开放性，国内团队更习惯强调 “技术领先”“市场份额”，这种叙事很难打动海外用户和资本。

第三是人才与生态适配问题。开源出海需要既懂技术、又懂海外市场规则和社区运营的复合型人才，国内这类人才很少。同时，海外开源生态的协作模式（跨地域远程协作、社区治理、基金会运作）和国内不一样，国内团队需要花时间适配，比如怎么和海外开发者沟通、怎么遵守基金会的治理规则、怎么融入当地社区，这些都需要学习成本。

不过我对未来还是有信心的。现在国内开源技术实力越来越强，很多团队已经开始重视海外规则和文化适配，加上基金会背书、社区共建等方式，未来 3-4 年应该会出现更多成功的出海案例。开源的核心是开放与协作，只要国内团队能保持开放的心态，主动适配海外生态，就一定能打破壁垒。

我一直觉得，中国的开源要想走向世界，必须保持开放的心态。开源社区的本质就是透明、协作、共享 —— 把代码开放出来，让全球开发者参与共建，既能吸收别人的优秀想法，又能让项目在多元反馈中不断完善。历史上的大唐盛世，就是因为开放包容，才吸引了世界各地的人来学习交流，创造了辉煌的文明；开源领域也是一样，只有开放才能凝聚更多力量，才能从 “强大” 走向 “伟大”。

很多人觉得开源是 “自损八百，伤敌一千”，觉得免费开放代码会让自己没饭吃，但其实不是这样。开源是一种更高效的协作模式，能快速建立信任、积累用户，在此基础上的商业化，反而更稳固、更长久。
